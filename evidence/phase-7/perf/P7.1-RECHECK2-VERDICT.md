## The assignment's hypothesis, and what I measured before touching any code

The instruction to investigate was: *"App shell chrome (TitleBar/TabBar/StatusLine)
re-rendering unmemoized on every keystroke via shared Zustand store."* Before applying
any fix, I built a temporary, no-op-unless-enabled render probe
(`apps/tui/src/util/render-probe.ts`, since removed) and instrumented `App`, `TitleBar`,
`TabBar`, `StatusLine`, `Panel`, and `BoardView`'s render bodies plus the `j` keybinding
handler, all gated behind an env var so it is completely inert in normal operation.

**Direct measurement result: the hypothesis is false.**

- A single isolated `j` keypress re-renders `BoardView` + its 3 `Panel`s only.
  `App`/`TitleBar`/`TabBar`/`StatusLine` render **zero** times per keystroke — they only
  render during the unrelated 2-second `setInterval(refreshTasks, 2000)` polling tick,
  confirmed by timestamp correlation.
- During a sustained 15-key burst, the `j` handler fired **4 times** (matching the
  measured drop rate), `BoardView` rendered **4 times**, its 3 `Panel`s rendered **4
  times each** — a clean 1:1 ratio, zero excess re-renders anywhere. `App`/`TitleBar`/
  `TabBar`/`StatusLine` again rendered **zero** times during the entire burst.

`App.tsx`'s Zustand subscriptions were already narrow, individual-field selectors
(`useAppStore((s) => s.view)`, `useAppStore((s) => s.themeName)`, etc. — never a broad
`(s) => s`), and `sel` (the value that changes on every `j`) lives entirely inside
`BoardView`'s own component state, never touching the shared store. There was nothing
unmemoized re-rendering per keystroke to fix.

## Where the real bottleneck is (source-verified, outside authorized scope)

Reading `node_modules/ink` directly (installed version 5.2.1) turned up two independent,
architectural mechanisms:

**1. Ink's own render throttle.** `node_modules/ink/build/ink.js:39`:
```js
this.rootNode.onRender = options.debug
    ? this.onRender
    : throttle(this.onRender, 32, { leading: true, trailing: true });
```
Ink caps its own terminal repaint to at most once per 32ms — a hard ~31.25fps ceiling,
independent of how fast React reconciles. **60fps is structurally unreachable in this
Ink version through any app-level optimization.**

**2. Ink's keypress parser processes one raw stdin `data` event as one keypress.**
`node_modules/ink/build/hooks/use-input.js:45-46` calls `parseKeypress(data)` once per
event. Verified directly:
```
$ node --input-type=module -e "
import parseKeypress from '.../ink/build/parse-keypress.js';
console.log(parseKeypress('j'));     // {name:'j', sequence:'j', ...}      correct
console.log(parseKeypress('jjjj'));  // {name:'', sequence:'jjjj', ...}    unrecognized
"
```
When the OS/PTY coalesces multiple rapid `j` bytes into one `data` event (inevitable
under sustained input faster than the process's read-loop drains it), Ink parses the
whole chunk as ONE unrecognized non-keypress. `use-input.js` then sets
`input = keypress.sequence = "jjjj"`; `apps/tui/src/hooks/useKeymap.ts`'s
`normalizeKey()` (line 34-35) returns `"jjjj"` verbatim; `ref.current["jjjj"]` is
`undefined` (only `"j"` is bound) — **the entire chunk is silently dropped**, contributing
zero scroll steps, not partial credit. This is the actual mechanism behind the measured
73-93% drop rates across all three stages.

Both mechanisms live in `node_modules/ink` (a dependency) and, for the dispatch step,
`apps/tui/src/hooks/useKeymap.ts` — which was **not** one of the files this task's scope
was extended to cover (the assignment named `BoardView.tsx`, `TitleBar.tsx`, `TabBar.tsx`,
`StatusLine.tsx`, `Panel.tsx`, and narrowly-scoped `App.tsx` selectors only). Fixing either
requires patching/vendoring/upgrading Ink or editing `useKeymap.ts`, both outside
authorized scope.

## What I changed anyway, and why

Even with the hypothesis disproven, `React.memo` on chrome components is still a
correct, low-risk hygiene improvement — components with referentially-stable props
should skip diffing when their parent re-renders for an unrelated reason (e.g. the
polling tick). I applied it honestly:

- **`TitleBar.tsx`, `TabBar.tsx`, `StatusLine.tsx`** — wrapped in `React.memo`.
  Documented in-code that this was measured-not-to-matter for the fps number, applied
  as hygiene only.
- **`Panel.tsx`** — deliberately **NOT** wrapped in `React.memo`. Its `children` prop is
  a fresh JSX tree on every call from `BoardView`; `React.memo`'s shallow comparison
  would never find `children` equal across renders, so the memo would be a no-op that
  *looks* like an optimization but never skips anything. Applying it anyway would have
  been a dishonest change. Documented the reasoning in-code instead of adding it.
- `App.tsx`'s Zustand selectors were already correctly narrow; no change made.

render-probe evidence exactly: there was nothing to fix at the React layer, so nothing
changed.

## Verdict: **FAIL (root cause outside authorized scope)**

The remaining scroll-throughput gap is not caused by anything fixable within
`apps/tui/src/views/BoardView.tsx`, the four named chrome components, `Panel.tsx`, or
`App.tsx`'s Zustand selectors — all of which were measured and found not to be the
bottleneck, or (for `App.tsx`) already correct. The real, source-verified cause is two
architectural properties of the `ink` npm package itself (a 32ms hard render throttle,
and a keypress parser that drops entire coalesced multi-character input chunks rather
than degrading gracefully), plus the app's `useKeymap.ts` dispatch faithfully rejecting
an unrecognized multi-character `input` string. Neither is addressable without either
patching/vendoring/upgrading the `ink` dependency or editing `useKeymap.ts`, both outside
the scope this task's boundary was extended to.

96.4ms → 94.3ms is the honest final number: a **statistically insignificant** change
from the windowing-only Stage 2 result. The task's own instruction — "a second honest
improvement that falls short is a legitimate result" — is exactly what this is, except
the improvement itself did not materialize because the diagnosed cause was wrong. That
diagnosis was tested, not assumed, and disproven with direct measurement before any code
was written, which is why the applied fix (React.memo) is real and correct but produced
no fps change.

**60fps is unreachable within this task's authorized file scope** — not because no
further optimization exists in principle, but because the actual remaining bottleneck
sits in a dependency (`node_modules/ink`) and a hook file (`useKeymap.ts`) that this
task was never authorized to touch.
