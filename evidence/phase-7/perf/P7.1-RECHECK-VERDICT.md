# P7.1 recheck — "200-task board scrolls at >=60fps" (post-fix)

This document is a **recheck**, not a replacement. The original run's artifacts
(`P7.1-RESULT.json`, `P7.1-VERDICT.md`) are unmodified and remain the record of the
pre-fix defect. This document adds the post-fix measurement, run with the identical
protocol, fixture, and trial counts, so the numbers are directly comparable.

## The fix

`apps/tui/src/views/BoardView.tsx` (the only file changed) previously `.map()`ed every
task in every status column unconditionally on every render. At 200 tasks that produced a
215-line-tall render tree that Ink had to diff and repaint on every keystroke, with nothing
to clip it — `Panel.tsx`'s `overflow="hidden"` never got a chance to act because nothing
bounded the panel's height to the terminal's real row count.

The fix flattens `groupByStatus(tasks)`'s output into a single header+item row list, then
renders only a window of that list sized to the real terminal height
(`useStdout().stdout.rows`, the same convention `PtyPane.tsx` already used), scrolled to
keep the selected task always visible. Column header counts (`BACKLOG (23)`, etc.) still
read the **true** per-status total, not the windowed subset — a reviewer scrolling to any
position sees correct counts, not counts of what happens to be on screen.

All existing keybindings and behavior (`j/k/up/down/H/L/return/s/x/l`, DETAIL pane,
AGENT STREAM, `moveTask`/`startTask`/stop calls) are unchanged — only the render layer
changed.

## Navigation correctness (checked before trusting any speed number)

A fast board that scrolls to the wrong task, or loses tasks, would be a worse outcome than
the original slow-but-correct board. This was checked first:

- Fired 200 sequential single keypresses from task 1 and recorded every column header's
  `(N)` count as it scrolled into view: **BACKLOG(23) + QUEUE(15) + BUILDING(23) +
  AI REVIEW(25) + HUMAN(39) + DONE(25) + ERROR(50) = 200** — identical breakdown to the
  original pre-fix measurement.
- Final selection after 200 presses: `200-fix-theme-tokens-200` — the last task, correctly
  reached.
- **Result: PASS.** The board is not just faster, it is still correct.

## Measurements: before vs after (identical protocol, identical fixture)

| Metric | Before | After | Change |
|---|---|---|---|
| M1 isolated keypress settle (median, 30 trials) | 10.0ms | 6.0ms | faster, both already under 16.67ms |
| M2 sustained-scroll registered/15 sent (avg, 8 trials) | 1.0 | 3.5 | 3.5x more keystrokes register |
| M2 sustained-scroll drop rate (median) | 93.33% | 76.67% | improved |
| M2 effective ms/registered-scroll-step | 296.7ms | 96.4ms | **3.08x faster** |
| M2 effective fps-equivalent | ~3.4 fps | ~10.4 fps | 3.08x |
| M3 20-task board drop rate (unchanged control, for reference) | 53.33% | 66.67% (noise) | no meaningful change, as expected |
| M0 control (`cat` process, PTY delivery integrity) | 50/50 delivered | 50/50 delivered | unchanged, as expected |

M3's lack of change is itself informative: a 20-task board already rendered its full list
in one paint before the fix (20 tasks fits well inside a ~40-row viewport), so windowing
had nothing to shrink there. The fact that M3 stayed flat while M2 improved 3x confirms the
M2 improvement is a real, targeted effect of bounding render size at scale — not a general
measurement drift or coincidence.

## Verdict: **FAIL (improved)**

The fix works and the improvement is real: **96.4ms per registered scroll step**, down from
**296.7ms**, a measured **3.08x speedup**, with navigation correctness fully preserved. But
96.4ms is still **~5.8x slower** than the 16.67ms/60fps budget the criterion specifies. This
is reported honestly as an improved-but-still-failing result rather than rounded up to PASS.

### What's likely still costing time (not attempted in this pass — file ownership was scoped to `BoardView.tsx` only)

- Viewport windowing bounds `BoardView`'s own row count, but the surrounding App shell
  (`TitleBar`, `TabBar`, `StatusLine`) lives in the same Ink render tree and re-renders on
  every keystroke via the shared Zustand store — those components were not touched and may
  not be memoized against props that didn't actually change.
- Ink's own reconciliation cost, even over a now-bounded ~40-row tree, plus the PTY
  write-and-flush cost for a full-width frame, are unmeasured contributors this fix did not
  target.
- `tuistory type()`'s own per-keystroke delivery overhead was ruled out as the *sole* cause
  by the M0 control and the M2-vs-M3 scaling comparison, but a lower floor in the instrument
  itself (below ~90-100ms) cannot be fully excluded without a lower-overhead measurement
  tool than what's available here.
