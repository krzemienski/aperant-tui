# P7.1 — "200-task board scrolls at >=60fps"

Source: `docs/plan/ROADMAP.md:16`. Prior status: PENDING (`docs/plan/ACCEPTANCE-INVENTORY.md:260`) —
"`build-fixture.py` builds only a handful of specs (4 in the observed template); no 200-task
fixture or fps measurement harness exists in `tools/`."

Both missing pieces were built, the measurement was run against the real app, and the criterion
is reported below with the actual number — including a finding that is unfavorable to the app.

## What was built

- **`tools/build-fixture-200.py`** (new file) — generates 200 real spec directories under
  `<project>/.auto-claude/specs/<NNN-slug>/`, each with `spec.md`, `requirements.json`,
  `task_metadata.json`, and an `implementation_plan.json` with a populated `phases[].subtasks[]`
  array, matching the exact field shape `apps/desktop/src/main/project-store.ts`'s
  `loadTasksFromSpecsDir` reads (verified by reading the source, not guessing). Statuses cycle
  through all 8 board columns the vendored `determineTaskStatusAndReason` maps to, so the board
  is populated realistically rather than dumping everything into one column. `git init`'d on
  branch `develop` with a commit, same convention as the existing `tools/build-fixture.py`.
- Fixture built into `/tmp/ap-perf-200` (never a real project directory).

## What was measured

The board was launched via the real app (`npx tsx src/cli.tsx /tmp/ap-perf-200`) driven through
`tools/tuistory_drive.py` against a live `tuistory` PTY session — no mocks, no simulated render
loop.

### Confirming 200 tasks actually render

The frame text at boot (`current_frame()`) shows column counts that sum exactly to 200:
`BACKLOG(23) + QUEUE(15) + BUILDING(23) + AI REVIEW(25) + HUMAN(39) + DONE(25) + ERROR(50) = 200`.
The title bar's `23 running` / `64 review` counters independently cross-check against
BUILDING=23 and (AI REVIEW 25 + HUMAN 39)=64. **The board renders all 200 tasks; nothing was
truncated or paginated away.**

### A PTY cannot give a GPU-style fps counter — what was measured instead

Two honest, distinct measurements were taken and are reported separately because they answer
different questions:

**M1 — isolated single-keypress settle latency.** With the full 200-task render tree already in
memory (steady state, not initial mount), one `j` is fired and the live terminal buffer is
sampled at a fixed 2ms cadence (`tuistory capture-frames`, which samples the raw PTY buffer
directly with no per-frame subprocess cost) until it hashes identical to its final value.
Across 30 trials: **median 10.0ms, mean 10.27ms, range 8-14ms.** Every one of the 30 samples is
under the 16.67ms (60fps) threshold. This says: *a single scroll step, in isolation, repaints
fast enough.*

**M2 — sustained rapid-scroll throughput (the actual "scrolling" scenario).** A user scrolling
doesn't send one isolated key; they hold/repeat it. 15 `j` characters were sent in a single
`tuistory type` call (the tool's built-in per-character pacing, no CLI-subprocess-per-keystroke
overhead — confirmed to deliver keys at ~125 attempted-keys/sec). The DETAIL panel's
authoritative `spec <id>` line was read before/after to count how many of the 15 keystrokes
actually registered as a visible selection/scroll change. Across 8 trials: **only 1 of 15
keystrokes registered every single time — a 93.3% drop rate**, for an effective throughput of
**~3.4 registered scroll-steps/sec, i.e. ~296.7ms per registered scroll step** — about **18x
slower** than the 16.67ms/60fps budget.

### Ruling out the instrument as the cause

A plain `cat` process (no React, no Ink, no app logic) was launched under the identical PTY
driver and sent the identical 50-character rapid burst. **50/50 characters were delivered and
echoed back intact.** This proves the PTY/tuistory delivery path reliably delivers 100% of rapid
keystrokes — the drop measured in M2 is a real application-level effect, not a harness artifact.

### Confirming the effect scales with board size (not a fixed terminal ceiling)

The identical M2 protocol was run against a 20-task fixture built with the same script
(`APERANT_PERF_N_TASKS=20`). Result: **46-67% drop (median 53.3%)** at 20 tasks vs **93.3%** at
200 tasks, under the same attempted input rate. If the ceiling were a fixed Node/terminal
input-batching limit independent of render cost, drop rate would not have moved with board size.
It did — sharply. This points at the render cost itself, not the terminal.

### Why: a real architectural finding, not a fluke

Reading `apps/tui/src/views/BoardView.tsx` (read-only, not modified — outside this task's
ownership boundary) shows **no scroll-viewport windowing exists**. `j`/`k` only move a `sel`
index; the component unconditionally `.map()`s and renders every task in every status column,
every render. `Panel.tsx`'s `overflow="hidden"` cannot clip this because nothing bounds the
TASKS panel's height to the terminal's row count — Ink measures intrinsic content height. A
single `current_frame()` capture at boot (sel=0, 50-row PTY) returned **215 total lines and 178
distinct task-id tokens visible in one paint** — essentially the entire 200-task flat list is
rendered every keystroke, not a fixed ~40-row scrolling window. This is the mechanism: as task
count grows, so does the per-keystroke render/diff cost, which is why the drop rate is
board-size-dependent rather than constant.

## Verdict: **FAIL**

The criterion "200-task board scrolls at >=60fps" is **FAIL**, not UNVERIFIED-instrument-
limitation. The instrument *can* resolve values well below the 16.67ms threshold (M1's 8-14ms
samples prove this), and a negative control (`cat`) proves the PTY delivery path is not the
bottleneck. The measured sustained-scroll throughput — the metric that actually corresponds to
what a user experiences when scrolling a 200-task board — is ~296.7ms per registered step
(~3.4 fps-equivalent), roughly 18x short of the 60fps target. This is a real defect, reproducible
across 8/8 trials at an identical drop rate (93.33% every time), with a plausible and
independently-verified root cause (unwindowed full-list re-render in `BoardView.tsx`).

Because `apps/tui/src/**` is out of scope for this task (owned by concurrently-editing workers),
no fix was attempted. The fix would be viewport-windowed rendering in `BoardView.tsx` (render
only the visible ~N rows around `sel`, keyed off terminal rows), which is a real, scoped, and
independently verifiable follow-up.
