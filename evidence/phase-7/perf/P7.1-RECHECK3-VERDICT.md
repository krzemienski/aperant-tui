## The fix

Stage 3 traced the real bottleneck to `node_modules/ink`'s single-keypress-per-
stdin-data-event assumption: when the PTY coalesces multiple rapid `j` bytes into
one `data` event, Ink's `parseKeypress` finds no recognized pattern and returns an
empty name; the whole chunk (e.g. `"jjjj"`) becomes `input` verbatim; `useKeymap.ts`'s
`normalizeKey` returns it unmodified; no binding matches; the **entire** chunk is
silently dropped.

The operator independently verified this mechanism by reading `useKeymap.ts:34-35`
and extended scope to that file. The fix:

- `useKeymap` gained an optional `splittableKeys?: string[]` — an **explicit,
  caller-provided opt-in allowlist**, defaulting to `undefined` (inert everywhere
  unless a view asks for it).
- When the whole-string lookup fails, and the failed name is a **uniform run of
  exactly one repeated character** (`name === name[0].repeat(name.length)`), and
  that character is in the caller's `splittableKeys` list, the matching binding is
  dispatched once per character instead of the chunk being dropped.
- A **mixed** run (`"jk"`, pasted text) never matches a uniform-run check and is
  never split — there is no way to know which handler(s) were intended for an
  ambiguous chunk, and firing the wrong one is worse than dropping it.
- **Only `BoardView.tsx` opts in, and only for `['j', 'k']`.** Verified by reading
  every other `useKeymap` call site in the codebase (`App.tsx` ×2, `AgentsView`,
  `InsightsView`, `LogsView`, `RoadmapView`, `SettingsView`, `TerminalView`,
  `WorktreeView`) — none pass `splittableKeys`, so the new code path is a
  guaranteed no-op for all of them.

`j`/`k` were chosen (and `H`/`L`/`s`/`x` deliberately excluded) because they are
pure `setSel((s) => Math.min/max(...))` functional-state-updater calls with zero
side effects — safe to fire N times synchronously in one React batch. `move()`
(bound to `H`/`L`) reads `task.status` from a per-render closure variable that does
not update mid-batch; N synchronous `H` calls would all attempt to move the *same*
stale task from the *same* stale status rather than converging correctly. `start()`'s
(bound to `s`) original reentrancy guard read `starting` component state the same
way — a coalesced multi-`s` chunk could have double-fired `startTask` (a real
process spawn) before this was noticed. As defense in depth, `start()`'s guard was
hardened to use a `useRef` (updates synchronously) instead of state, even though
`s` is not in the split allowlist.

### Why this cannot intercept typing in the Insights ask box

Proven by construction, not by a new guard added for this fix:

1. `InsightsView.tsx`'s `useKeymap({...}, {isActive: isActive && !asking})` passes
   no `splittableKeys` — the split path never runs for this call site regardless of
   `asking`.
2. When `asking` is true, `isActive` becomes false. Ink's own `useInput`
   (`node_modules/ink/build/hooks/use-input.js:32-35, 41-44`) never subscribes its
   `input` listener when `isActive` is false — the callback, and therefore this
   fix's code, cannot fire while the ask box is open.
3. `ink-text-input`'s `TextInput` registers its own, entirely separate `useInput`
   instance and never touches `useKeymap.ts`.

Verified live: typed `"does j:k scroll work? test"` — deliberately including
literal `?` and `:`, the exact characters `App.tsx`'s D18 comment documents as
otherwise captured by the global help/palette keymap — into the ask box. The full
string landed intact; no overlay opened.

## The honest remainder: an instrument ceiling, not an app ceiling

22.39ms/step still exceeds the 16.67ms/60fps threshold. Before reporting that as
"the app's speed," I measured what it actually is, using a temporary
high-resolution probe (`process.hrtime.bigint()`, removed after use, same
discipline as the Stage 3 investigation):

- All 15 `j` handler invocations, 5 `BoardView` re-renders, and the resulting
  correct scroll (task 1 → 16) completed within **~20.3ms of the first
  keystroke's handler firing.**
- `tuistory type()` itself did not return control to the test script for another
  **~313ms** after that.
- Independently timed `tuistory type('j'*15)` against a **plain `cat` process**
  (zero app logic, zero React, zero Ink) under the identical session setup:
  **315.2ms for 15 characters = 21.01ms/char** — statistically indistinguishable
  from the app's measured 22.39ms/registered-step.

`tuistory type` has a fixed, undocumented per-character delivery pacing of
~21ms/char (no configuration flag exposed per `tuistory type --help`) that exists
independent of any application under test. That pacing is itself *below* the
16.67ms/60fps target rate — meaning **M2, as measured via `type()`, can no longer
distinguish "the app processes keys in <16.67ms each" from "the app processes keys
in ~21ms each."** The instrument's own floor now sits inside the range being
measured. Extrapolated app-side-only throughput from the probe data: ~1.36ms per
keystroke (15 keys in ~20.3ms), implying roughly 736 keystrokes/sec of real
capacity — far beyond the 60/sec the criterion requires. This is reported as a
secondary, probe-derived finding, not substituted for the M2 headline number,
because it came from a different instrument than the standard protocol.

## Ink's architectural ceiling, restated with arithmetic

Independent of the above, and unconditionally true regardless of app-side fixes:

```
node_modules/ink/build/ink.js:39
this.rootNode.onRender = throttle(this.onRender, 32, { leading: true, trailing: true });
```

- Throttle interval: **32ms**
- Maximum sustained repaint rate: `1000 / 32 = 31.25 fps`
- Target: `1000 / 60 = 16.67 ms/frame`
- Ratio: `32 / 16.67 = 1.92x` — Ink's own hard floor is **1.92x slower** than the
  target requires

Even in the theoretical limit of zero app-side processing time, Ink 5.2.1's own
`throttle()` wrapper caps sustained repaint at 31.25fps for **any** application
built on it. This measurement chain never actually reached that 32ms ceiling as
the binding constraint — the `tuistory type()` instrument's own ~21ms floor
intervened first — but it stands as a documented, source-verified, unconditional
fact from the Stage 3 investigation, unaffected by this stage's fix.

## Verdict: **FAIL** — drop-rate defect fixed (8.3x); remaining gap is Ink's own architecture

The actual defect this investigation was chasing — silently dropped keystrokes
under sustained scroll — is **fixed**: 93.33% drop (Stage 1) → 0% drop (Stage 4),
an 8.3x throughput improvement (~3.4fps → ~44.7fps by the M2 metric), with zero
behavioral regressions. That is real, measured, and verified.

The criterion still reads FAIL on the raw 22.39ms number, but the honest breakdown
is: the app's own keystroke-processing cost is now far under the 16.67ms budget
(~1.36ms/key, probe-measured); the 22.39ms figure is dominated by the measurement
instrument's own delivery pacing, not the app; and — separately, unconditionally,
and untouched by any fix available within this task's scope — Ink 5.2.1's
hard-coded 32ms render throttle caps *any* Ink application at 31.25fps, 1.92x
short of 60fps, by design.

**60fps is architecturally unreachable within `apps/tui/src/**` as currently
built on Ink 5.2.1.** A fix would require one of:

1. **Vendoring or patching** `node_modules/ink/build/ink.js`'s `throttle(this.onRender, 32, ...)` call to a smaller interval (or removing the throttle), verifying Ink's reconciler and terminal-write pipeline tolerate the higher paint rate without new flicker/tearing artifacts.
2. **Upgrading** the `ink` dependency to a future major version, if one exists or is ever released, that removes or exposes this throttle as configurable.

Both are dependency decisions for the operator, explicitly out of scope for this
task per instruction ("Do NOT patch or vendor `node_modules/ink`"). This report
states that plainly rather than either declaring a false PASS or leaving the
ceiling unexplained.
