# P6.3-RECHECK — "Onboarding completes on a machine with no `~/.aperant/` and ends in a working board"

## Verdict: PASS

This recheck **does not overwrite** `P6.3-RESULT.json` / `P6.3-VERDICT.md` — it
stands alongside them as strengthened evidence in response to a specific,
fair reviewer objection.

## The objection being answered

> P6.3-RESULT does not demonstrate "onboarding completes": it only boots with
> zero accounts, switches to Settings, and explicitly says no `tui.json` was
> written and no agent ran. Unless the product defines boot-with-defaults as
> onboarding (must cite source), keep P6.3 PARTIAL/UNVERIFIED; a cold-start
> board render alone is insufficient.

## Step 1 — What does "onboarding" mean in this product?

**Finding: (b)** — the Aperant TUI has **no distinct onboarding
wizard/flow/screen**. There is no first-run detector, no setup prompt
sequence, no "welcome" state distinct from the steady-state board.

Search performed: `grep -i 'onboard|firstRun|first-run|welcome|setup|wizard'`
across `apps/tui/src/**`, `apps/desktop/src/main/**`, `libs/**`, `README.md`,
`docs/**`.

Citations:

- **`apps/tui/src/services/config-service.ts:27-29`** — `loadConfig()`:
  `if (!fs.existsSync(p)) return TuiConfigSchema.parse({})`. Pure lazy-default
  read. No wizard, no prompt, no gate.
- **`libs/electron-shim/index.js:36,49-51`** — `userData` resolves to
  `APERANT_USER_DATA` (test override) or `~/.aperant`; directories are
  silently `mkdirSync(recursive:true)`'d on module load. No first-launch
  detection logic exists here at all.
- **`apps/tui/src/App.tsx:227-229`** — the only conditional first-frame
  states are `"opening {projectPath}…"` (a brief loading state) and an error
  box for `openError`. There is **no branch distinguishing a first run from
  a returning user** — the board is the single steady-state destination for
  both.
- **`docs/plan/ROADMAP.md:15`** / **`docs/plan/ACCEPTANCE-INVENTORY.md:232-246`**
  ("Context, Settings, Onboarding") — the word "Onboarding" in this repo's
  own planning docs is used **only** as this gate's section label. No other
  planning doc (`phase-*-PLAN.md`, `phase-*-VALIDATION.md`) defines a
  distinct TUI onboarding flow anywhere.
- **Important distinction**: the `onboard`-matching hits that *do* exist
  (`apps/desktop/src/main/claude-profile/credential-utils.ts`,
  `cli-integration-handler.ts`, `ipc-handlers/settings-handlers.ts`,
  `__tests__/ensure-onboarding-complete.test.ts`, `output-parser.ts`) are
  **Claude Code's own onboarding wizard** — the vendored CLI binary the
  *desktop* app shells out to — being suppressed via
  `ensureOnboardingComplete()` for already-authenticated profiles. This is
  unrelated to Aperant's own TUI cold-start behavior: it governs whether the
  wrapped `claude` process shows *its* welcome screen, not whether Aperant
  itself has a setup flow. None of that code path is reachable from a TUI
  cold boot where no agent is started (true in both the prior run and this
  recheck).

**Conclusion:** given (b), the only defensible reading of P6.3 is: on a
machine with zero prior config/settings history, the app must (i) boot
without crashing, (ii) create its own dirs/defaults gracefully, (iii) render
a genuinely *working*, interactive board, and (iv) support the user
completing real first-time setup (theme, account) that durably persists.
The prior run proved (i), (ii), and a static render of (iii) but never
exercised the durable-write path or interactivity — which is exactly what
the reviewer flagged. This recheck closes that gap.

## Final verdict: **PASS**

The reviewer's objection is answered with new evidence, not by redefining
the criterion in the product's favor:

1. Step 1 establishes, with source citations, that this product has no
   distinct onboarding wizard for the TUI — cold-start-to-working-board is
   the only reading the codebase supports, so driving that path *is* driving
   "onboarding" as this product actually defines it.
2. Each specific gap the reviewer named is now closed with evidence
   stronger than the prior run: a real UI-triggered `tui.json` write,
   verified on disk and confirmed to survive a full process restart; an
   interactive (not static) board proof across all 7 views with zero crash
   markers across two full process lifecycles; and a real provider account
   provisioned through the TUI's own flow, written to `settings.json` in
   the exact vendored shape, zero secret leakage, and confirmed to persist
   across a restart.
3. The one field that did not change (`no profile` header text) is reported
   honestly as out of scope, with the source citation explaining why it
   belongs to a different subsystem than the one this criterion's account-
   provisioning claim addresses.
