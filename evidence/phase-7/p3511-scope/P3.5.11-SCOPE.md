## 1. Independent confirmation of the reference-count claim

result file.

| # | File:line | Role |

**Correction to the prior result's routing table:** the prior doc's
`P3.5.11-RESULT.json` step 3 cites `iterateSubtasks` / `build_orchestrator`
as also "routing around" the agentic path, which is true but for a
different reason worth stating precisely: `build_orchestrator` sessions
**never check `useAgenticOrchestration` at all** —
`worker.ts:420-424` routes `agentType === 'build_orchestrator'`
unconditionally to `runBuildOrchestrator()`, with no flag branch. Only
`spec_orchestrator` sessions have an agentic/non-agentic fork. This matters
for blast-radius scoping in §4 below: the flag, even if flipped, can never
affect the coding/build phase of a task — only the spec-creation phase.

## 2. The full downstream path — is it half-built, or does it work?

Traced `runAgenticSpecOrchestrator` end to end
(`apps/desktop/src/main/ai/agent/worker.ts:997-1150`). Every link in the
chain is **implemented, not stubbed**:

1. **Tool declared:** `spawnSubagentTool` —
   `apps/desktop/src/main/ai/tools/builtin/spawn-subagent.ts:95-155`.
   Full `Tool.define()` with real input schema, description, and an
   `execute()` that pulls a `SubagentExecutor` off `ToolContext` and calls
   `.spawn()`. Graceful (not silently broken) if no executor is present:
   returns an explanatory error string, exercised only in non-agentic
   sessions where the tool would not have been offered anyway.

2. **Tool registered for the orchestrator LLM:**
   `apps/desktop/src/main/ai/config/agent-configs.ts:235-236` —
   `spec_orchestrator: { tools: [...ALL_BUILTIN_TOOLS, 'SpawnSubagent'], ... }`.
   `runAgenticSpecOrchestrator` (`worker.ts:1076-1079`) pulls this via
   `registry.getToolsForAgent('spec_orchestrator', orchestratorToolContext)`
   and merges it into the `SessionConfig.tools` map that
   `runContinuableSession` hands to `streamText()`. The orchestrator LLM
   genuinely receives the tool in its tool list.

3. **Handler is real, not a stub:**
   `SubagentExecutorImpl.spawn()` —
   `apps/desktop/src/main/ai/orchestration/subagent-executor.ts:117-196`.
   Loads a real subagent system prompt (`loadPrompt`), builds a real,
   recursion-safe tool set (explicitly excludes `SpawnSubagent` at
   line 137 — "No recursion"), and calls a real `generateText()`
   (`ai` SDK) with the subagent's own model/tools/messages. This is a
   complete, working nested-agent execution — not a placeholder.

4. **Wired into `runAgenticSpecOrchestrator`:**
   `worker.ts:1034-1053` constructs the `SubagentExecutorImpl`, attaches it
   to an extended `ToolContext` (`subagentExecutor: executor`), and passes
   that context through to tool binding — so the tool's `execute()` really
   can find the executor at runtime.

**Conclusion for §2:** if the flag were `true`, a working
`SpawnSubagent` tool-call loop **would** occur — this is not a half-built
path with a declared-but-unregistered tool or a stub handler. All four
layers (declaration, registration, handler, wiring) are functionally
complete.

## 2b. A gap the prior investigation did not surface: the observability tap does NOT create graph nodes

This is the one new finding from this session's independent trace, and it
changes the shape of the recommendation.

- The `SpawnSubagent` **tool-call itself** (issued by the orchestrator LLM)
  flows through the normal event pipeline:
  `streamText()` fullStream → `emitEvent` (`runner.ts:389-407`) →
  `onEvent` → `postMessage({ type: 'stream-event', ... })`
  (`worker.ts:1110-1116`) → `observability.ts` `onStreamEvent()`
  (`observability.ts:367-376`) → `pushTrace(taskId, 'tool-call',
  'SpawnSubagent', ...)`. This **is** observable in tab 7's **Trace** and
  **Waits** sub-views: it would appear as a `tool-call SpawnSubagent` trace
  line and, while the call is in flight, as `kind: 'tool', toolName:
  'SpawnSubagent'` in the waits panel.

- **However**, the subagent's *own* execution — everything inside
  `SubagentExecutorImpl.spawn()`, including its `generateText()` call — is
  **not connected to the event pipeline at all**. `spawn()` calls
  `generateText(generateOptions)` directly (`subagent-executor.ts:169`)
  with no `onStepFinish`/streaming hook wired back to `postMessage`. The
  only observability surface for subagent lifecycle is the
  `onSubagentEvent` callback (`worker.ts:1043-1045`):
  ```ts
  onSubagentEvent: (agentType: string, event: string) => {
    postLog(`Subagent ${agentType}: ${event}`);
  },
  ```
  This posts a **free-text `log` message under the SAME `taskId`** as the
  parent orchestrator (`postLog` is bound to module-level `config.taskId`,
  confirmed at `worker.ts:74,97-98` — one worker thread = one task = one
  taskId for its entire lifetime). `observability.ts`'s `onLog` handler
  (`observability.ts:306-308`) only pattern-matches a *different* specific
  log line (`SESSION_START_RE`, the initial model-resolution line) — it
  does nothing with arbitrary `Subagent ${agentType}: ${event}` text.

- **The graph-node mechanism specifically:** `AgentSnapshot.parentId` is
  declared `string | null` (`observability.ts:63`) and `GraphView`
  (`apps/tui/src/views/AgentsView.tsx:225-234`) builds its tree by
  grouping agents with `byParent.get(a.parentId)`. I grepped every
  reference to `parentId` in both `apps/desktop/src` and `apps/tui/src`:
  it is set to `null` exactly once, unconditionally, in `ensureAgent()`
  (`observability.ts:253`), and **read** (never written a second time)
  in `GraphView`. There is **no code path anywhere in the repository**
  that ever constructs a second `AgentSnapshot` with a non-null
  `parentId`. Even a fully agentic run with real `SpawnSubagent` traffic
  would still show only one root node in `GraphView` — the orchestrator —
  because nothing creates a distinct child snapshot for the spawned
  subagent.

**Precise implication:** flipping `useAgenticOrchestration` alone
satisfies the *weaker* reading of the criterion text ("a SpawnSubagent
tool-call loop must actually occur and be observable... in tab 7") via the
Trace/Waits sub-views, but does **not** satisfy the criterion's own title
("Graph topology — subagent nodes") — no second, connected node would ever
render in `GraphView`, with or without the flag.

## 3. Injection point(s)

- **Existing, real config surface exists and is the correct location.**
  `apps/desktop/src/main/agent/types.ts:64-90` (`SpecCreationMetadata`)
  already carries exactly this kind of per-task opt-in boolean —
  `useWorktree?: boolean`, `useLocalBranch?: boolean`,
  `requireReviewBeforeCoding?: boolean` are all precedent for a
  `useAgenticOrchestration?: boolean` sibling field.
- `startSpecCreation()` (`apps/desktop/src/main/agent/agent-manager.ts:342-438`)
  is the single real construction site for the `spec_orchestrator`
  session config; it already reads other `metadata?.*` fields the same
  way (e.g. `metadata?.requireReviewBeforeCoding` at line 415). Adding
  `useAgenticOrchestration: metadata?.useAgenticOrchestration === true,`
  to the `sessionConfig` literal (around line 408-438) is the natural,
  minimal-diff injection point.
- I did not trace how `SpecCreationMetadata` itself is populated upstream
  (IPC handlers / TUI settings surface) — that is out of scope for this
  read-only pass, but the pattern for exposing a new sibling boolean
  through that same metadata object already exists for the other three
  fields, so it is not an invented surface.

## 4. Blast radius

- **Scoped by construction, not by accident.** Because `worker.ts:432-440`
  only checks the flag for `agentType === 'spec_orchestrator'` sessions,
  and `build_orchestrator` sessions never consult it at all (§1), the
  *only* phase of a task that could ever be affected is **spec creation**
  — never planning/coding/QA.
- **Global vs opt-in is a design choice at the injection point, not a
  structural constraint.** If wired as `metadata?.useAgenticOrchestration
  === true` (default `undefined`/falsy), the change is a genuine per-task
  opt-in: every existing task and every task that doesn't explicitly set
  the new metadata field keeps today's exact behavior
  (`runSpecOrchestrator()`, the hardcoded sequential pipeline). Only a
  task that explicitly opts in would ever exercise
  `runAgenticSpecOrchestrator()`.
- No other subsystem, session type, or default code path changes.

## Verdict: **BOUNDED**

Two coordinated, small, additive, opt-in changes — not missing
architecture. All four SpawnSubagent-loop layers (tool, registration,
handler, wiring) already exist and work; nothing needs to be built from
scratch. What's missing is (a) a way to turn the existing agentic path on
for a given task, and (b) a small addition to the existing observability
tap so a spawned subagent gets its own graph node.

   (Requires threading a stable `subagentId` through
