### How the single-frame capture was obtained

Diagnosis: the frame-stacking defect is triggered specifically by the worker process's raw
(non-Ink-managed) `console.log` calls at agent-start time — lines like
`[ClaudeProfileManager] Starting initialization...`, `[WorktreeManager] ...`,
`[AgentManager] ...` — which write directly to the PTY stream outside Ink's cursor-tracking
render loop. This permanently shifts Ink's redraw anchor down by the number of raw log lines
printed, so the pre-shift frame remains fixed in the emulator's buffer forever (confirmed
experimentally: frame count stayed at 2 across 4+ subsequent idle polls and further keypresses —
it never self-heals). Since the terminal was sized 200x50 and the pre/post-shift frames are only
~20 rows each, both fit simultaneously in the 50-row buffer and both get rasterized by
`screenshot`.

The fix: `tuistory resize <cols> <rows>` followed by resizing back to the original dimensions
genuinely clears the terminal emulator's scrollback/back-buffer (confirmed: `resize 200 10` then
`resize 200 50` collapsed the sidecar from 2 `APERANT` occurrences to 1, with the live application
state — real running agent, real `phase planning` value — fully intact and correctly laid out
afterward, not reset or corrupted). This is a genuine terminal-buffer clear, not a lucky
coincidence: verified by checking `task_logs.json`'s `updated_at` continued advancing across the
resize (proving the real agent process kept running throughout) and that `implementation_plan.json`
remained absent on disk immediately before and after.

`tools/tuistory_drive.py` has no dedicated "clear scrollback" primitive; the resize-down/resize-up
round trip is the only reliable one this tool version exposes (confirmed by reading
`tuistory --help`'s full command list: `launch`, `snapshot`, `read`, `screenshot`, `type`, `press`,
`click`, `click-at`, `wait`, `wait-idle`, `scroll`, `resize`, `capture-frames`, `close`, `restart`,
`sessions`, `logfile`, `daemon-stop`, `attach` — no `clear` command exists).

## Root cause: `tuistory screenshot` captures scrollback, and `wait()`→`screenshot()` has a gap

`tools/tuistory_drive.py`'s `shot()` (lines 169–204) works like this:
1. `wait(session, anchor)` polls the live buffer until `anchor` text appears, then returns.
2. `screenshot -s session -o out.png` is invoked as a **separate subprocess call** afterward.
3. Between (1) returning and (2)'s shutter actually firing, the TUI can re-render — and did.

Ink repaints the *entire* terminal each time state changes, which pushes the previous render into
terminal scrollback. `tuistory screenshot` rasterizes the terminal's on-screen buffer at shutter
time, and the vertical space needed to also cover the freshly-scrolled-up prior render pushed that
older, stale-relative-to-shutter frame into the same PNG, stacked above the current one — exactly
as `tuistory_drive.py`'s own `current_frame()` docstring warns about for `snapshot()` output
(lines 99–111: *"Worker/CLI writes to the terminal push previous frames up into scrollback... a
naive substring check matches text from a frame that is no longer on screen"*). I read that
docstring, wrote code that correctly applies its "last frame wins" rule when parsing `snapshot()`
text — but never applied the same discipline when *reading a PNG*, where the equivalent job is
"trust only the bottom of the image, not just whatever anchor text appears anywhere in it."

The anchor mechanism only guarantees the anchor string appeared *at some point before the shutter
fired* — not that it is still present in the frame the shutter actually captured. `phase planning`
was a genuinely transient state: it appeared once as the agent started (`03:45:54`), then reverted
to `-` before the actual `screenshot` subprocess call completed (the field went transiently
non-idle then the live tap's own filter, `if (a.phase && a.phase !== 'idle') m.set(...)` at
`BoardView.tsx:125`, stopped surfacing it once the underlying `AgentSnapshot.phase` cycled back to
`idle` — visible later in `step-02`'s tab-7 INSPECT view, `phase idle ~ inferred`, at the same
early point in the run).

## Lesson for future anchor-gated captures with this tool

`tuistory_drive.py`'s anchor mechanism (`wait()` before `screenshot()`) guards against capturing a
frame *before* the expected state appears, but does **not** guard against the state having already
moved on by the time the shutter actually fires, nor against the resulting PNG containing more
than one rendered frame stacked in scrollback. Any claim resting on a single anchor-gated PNG
should be corroborated against its `.png.txt` sidecar, checking specifically the **last** frame
(matching the rule in `current_frame()`), not just "does the anchor text appear somewhere in the
image." I did not do this at capture time for `step-01`; I have now done it retroactively for
every capture in this run (see `frame-decomposition-analysis.json`).
