## 2. Signal selected: **Option 2 — phase ordinal (phase-granular progress)**

**Option 1 (real subtask counts from the live tap) was ruled out after
independent trace**, not assumed absent:
- `AgentSnapshot` (`observability.ts:56-81`) carries `subtaskId?: string`
  (a free-text id/index, populated by regex extraction
  `/subtask[:\s]+(\d+(?:\/\d+)?|\w+[-_]\w+)/i` over log text or tool-call
  args `subtask_id`/`subtaskId` — see
  `apps/desktop/src/main/ai/session/progress-tracker.ts:385-388` and
  `apps/desktop/src/main/agent/parsers/execution-phase-parser.ts:151-157`).
  It never carries a paired total.
- The genuine real counts (`totalSubtasks`, `completedSubtasks`) exist —
  computed by `subtask-iterator.ts`'s `countTotalSubtasks`/
  `countCompletedSubtasks` from the actual `implementation_plan.json` — but
  I traced the call path and confirmed `worker.ts`'s `runBuildOrchestrator`
  never forwards those onto any `postMessage`/`execution-progress` payload.
  They live and die inside the subtask-iteration loop; the observability tap
  genuinely never receives them.
- `onProgress()` in `observability.ts:276-289` destructures only
  `{ phase, currentSubtask, message }` from the incoming event — it does
  not even read `progress.phaseProgress` or `progress.overallProgress`,
  which the worker-thread path (the actual path for `build_orchestrator`
  runs — confirmed via `worker-bridge.ts:13` `import { Worker } from
  'worker_threads'`) hardcodes to `phaseProgress: 0, overallProgress: 0`
  with the comment **"Detailed progress calculated by UI from phase"**
  (`worker-bridge.ts:210-221`, `emitProgressFromTracker`). This is the
  vendored runtime explicitly telling the consumer, by design, that no
  finer-grained number is coming over this channel.
- `stepsExecuted / maxSteps` (`AgentSnapshot.stepsExecuted`,
  `AgentSnapshot.maxSteps`) was rejected per the interjection: `maxSteps`
  is hardcoded to `1000` at `ensureAgent()` (`observability.ts:258`) and
  never reassigned anywhere in the codebase (grepped `\.maxSteps\b` across
  `apps/tui/src` — zero write sites). It is a safety ceiling unrelated to
  actual task size; a task finishing in 40 steps would render `4%` at
  completion — dishonest, worse than the prior `0%`.

**What IS genuinely known and fixed**: `EXECUTION_PHASES`
(`apps/desktop/src/shared/constants/phase-protocol.ts:26-36`) is a closed,
ordered set — `idle, planning, coding, rate_limit_paused,
auth_failure_paused, qa_review, qa_fixing, complete, failed` — with a
canonical weight mapping `EXECUTION_PHASE_WEIGHTS`
(`apps/desktop/src/shared/constants/task.ts:121-`) that `observability.ts`'s
`PHASE_WEIGHTS` mirrors byte-for-byte
(`planning:[0,20], coding:[20,80], qa_review:[80,95], qa_fixing:[80,95],
complete:[100,100]`). `overallProgress(phase, 0)` — the exact function
already exported from `observability.ts:568-573` and already used this
exact way at `AgentsView.tsx:241` for the ORCHESTRATION GRAPH view — gives
a phase-floor percentage that is **honest**: it reflects a real,
server-confirmed phase transition every time it changes, and never
fabricates a per-step or per-subtask count that was never observed. It is
explicitly **phase-granular, not work-granular**: it advances in four
discrete steps (0→20→80→95→100), not smoothly.

## 3. Fix

`apps/tui/src/views/BoardView.tsx`:
- `progressOf(t: Task, live?: number)` now accepts an optional live value
  and returns it verbatim when present, falling through to the
  byte-for-byte original disk-derived computation otherwise (fallback
  preserved bit-for-bit — confirmed by diff, no logic in the disk branches
  changed).
- `livePctByTaskId` (new `useMemo`, same `[liveTick]` trigger as the
  existing `livePhaseByTaskId`) derives `overallProgress(a.phase, 0)` per
  live agent.
- `pctHighWaterMark`: a **module-level** `Map<string, number>` (not a
  component `useRef`) clamps each taskId's live percentage to never
  decrease. This guards two real regressions:
  1. `overallProgress()` returns `0` for phases outside `PHASE_WEIGHTS`
     (`failed`, `rate_limit_paused`, `auth_failure_paused` have no band) —
     a task that reaches `qa_review` (80%) and then fails would otherwise
     visibly drop to `0%`.
  2. **Found live, during this drive, and fixed**: my first implementation
     used a component-local `useRef`. `App.tsx:246` conditionally mounts
     `BoardView` only while `view === 'board'` — switching to tab 7
     (AGENTS) and back unmounts/remounts `BoardView`, creating a fresh
     `useRef(new Map())` on every remount. I reproduced this directly:
     switched to the agents tab and back mid-run, and watched the DETAIL
     panel's `progress` value drop from `20%` back to `0%` (with `phase`
     also visibly bouncing back to the stale-heuristic `planning`) while
     the live agent (same phase, still running underneath, token count
     still climbing) was untouched. Moving the map to module scope
     (matching the file's existing `observability` singleton convention)
     fixed it; re-verified live (see capture A below) that the value now
     survives a tab-away-and-back.

Files touched: `apps/tui/src/views/BoardView.tsx` only (first-party
`apps/tui/**`; no `apps/desktop/**` edits, no vendored-patch marker
required). P7.1 viewport windowing (`boardRows`/`viewportRows`/`scrollRef`/
`visibleRows`) and the `splittableKeys: ['j','k']` keymap opt-in were not
touched — confirmed by diff (only edits: import line, `progressOf` header
comment + signature, `pctHighWaterMark` module const, `livePctByTaskId`
memo insertion, and the three call-site updates threading `livePct`).
