## Blocker hit and fixed (real, not simulated)

**"Authentication required. Please add an account in Settings > Accounts before starting tasks."**

Root-caused by reading source, not guessing:
- `apps/desktop/src/main/agent/agent-manager.ts:361,481,632` — `startTask`/related paths gate on `profileManager.hasValidAuth() || hasAnyProviderAccount()`. Neither checks `ANTHROPIC_AUTH_TOKEN`/`ANTHROPIC_API_KEY` env vars directly — only a Claude CLI OAuth profile or a `providerAccounts[]` entry in `settings.json`.
- My isolated `APERANT_USER_DATA=/tmp/aperant-userdata-pp2` sandbox (used deliberately per the task's constraint to never touch the operator's real `~/.aperant/settings.json`) started with 0 provider accounts and no profile, so the gate correctly refused.
- Fix (no code change needed — a real app feature): went to Settings (tab 6), pressed `a` (`SettingsView.tsx:77-81` → `provisionAnthropicAccount()`), which auto-provisions an Anthropic-compatible account from the `ANTHROPIC_AUTH_TOKEN`/`ANTHROPIC_BASE_URL` env vars already forwarded to the session. Settings then showed `provider anthropic`, `queue 1 account → http://127.0.0.1:20128/v1`. Re-pressing `s` immediately succeeded.
- Verified this is environmental (isolated sandbox with zero pre-provisioned account), not an app bug: `applyAccountEnv()` in `agent-start-service.ts:405-447` is called by the roadmap generation path and DOES fall back to `ANTHROPIC_AUTH_TOKEN → ANTHROPIC_API_KEY`, which is why roadmap generation (`g`/`G`) never needed provisioning — but the task-start gate (`hasValidAuth()||hasAnyProviderAccount()`) is a separate precondition checked BEFORE `applyAccountEnv()` runs for that code path, and it only recognizes a persisted profile/account, not a bare env var. This is a real, reproducible precondition-gate design (any fresh-sandbox TUI user hitting `s` before visiting Settings once would see the same message) — not a defect introduced by this session, and not something I patched in the source, since the app's own real "provision from env" feature (`a` in Settings) is the intended fix path.

## Known no-code-change findings worth flagging

1. **`g` (lowercase, refresh=false) genuinely no-ops when a roadmap already exists** — this is by design (`roadmap.ts:110-112,229-231`), not a bug, but it means the task brief's suggestion to check the keymap before choosing `g` vs `G` was correct and necessary; a naive driver pressing `g` first would have produced a false "no streaming" finding.
2. **[ROOT-CAUSED + FIXED + VERIFIED] Board tab's phase/progress display did not refresh live during coding.** Root cause (verified by reading source, not inference): `BoardView.tsx`'s DETAIL phase line read `task.executionProgress?.phase`, which `project-store.ts` derives ONLY from the main repo's on-disk `implementation_plan.json.executionPhase`. That file never exists in the main repo during a live worktree run — `BuildOrchestratorConfig.syncSpecToSource` (`build-orchestrator.ts:99,366-368,391-393,482-484`), the only mechanism that would sync it there live, is declared optional and is **never supplied** by `worker.ts`'s `runBuildOrchestrator` (verified: no `syncSpecToSource:` key anywhere in that object literal at `worker.ts:577-615`) — every guard on it is dead code. The partial per-subtask `syncPhasesToMain()` (`subtask-iterator.ts:363-390`) can only UPDATE an existing main-plan file, never CREATE one (silent no-op on `ENOENT`). The TUI's own `F-17` fix (`agent-start-service.ts:202-283`) DOES create the main plan — but only on the process `exit` event, by design, which is exactly why the main-repo plan (and `task.executionProgress`) never existed until the run was already over. **Fix**: subscribed `BoardView.tsx` to the same event-driven `observability` tap tab 7 (`AgentsView.tsx`) already uses (`observability.on('snapshot', ...)` + `getAgents()`, keyed by `taskId`) — no new disk polling, no changes to any vendored desktop file. Falls back to the disk-derived value when no live agent is tracked. **Verified by driving a fresh task** (`006-tool-allow-deny-lists`, converted and started in this same session): DETAIL showed `phase planning` in live color **the instant `s` was pressed, while `implementation_plan.json` was confirmed absent from the main repo's disk** — unambiguous proof the value comes from the live tap, not disk. 4 distinct-hash captures in `BOARD-LIVE-PROGRESS-FIX.json`. **Secondary finding (separate, pre-existing, NOT introduced by this fix, left unfixed as out of scope)**: `observability`'s own `phase` field itself sometimes goes stale mid-run for the coding-phase transition specifically — reproduced identically on tab 7's own swarm/inspect views at the same wall-clock moment, so the board now has full parity with the app's existing live-observability standard, not a new independent (and possibly worse) data path. Full analysis in `BOARD-LIVE-PROGRESS-FIX.json`.
3. **CODING_FAILED bug from the brief was not encountered, across the full run** — the two cited fixes (`models.ts` context-window prefix strip, `stream-handler.ts:279` `promptTokens=` assignment) were verified present in the worker bundle twice: once before the agent's first start, and again after rebuilding the bundle mid-run when told the source had been touched again. The complete 9-subtask coding phase and the full validation phase both finished cleanly with no `implementation_plan.json`-not-found error and no observed context-window miscalculation.
4. **The plan's own subtask count is internally inconsistent** — `implementation_plan.json.summary.total_subtasks` says `8`, but `implementation_plan.json.phases[].subtasks` actually lists 9 subtask objects (`subtask-1-1` through `subtask-6-1`). All 9 were committed. This is a cosmetic bug in the plan the agent itself generated, not a bug in aperant-tui; noted for completeness since it could otherwise look like a discrepancy in this verdict's own counting.
